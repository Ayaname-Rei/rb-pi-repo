## 一、现在的运动设计思路

### 1.1 一句话概括

**"19 段相对位移定线巡航 + 板端里程计闭环 + 行为树按段驱动 + 抓取任务配置化插入"**：
上层（树莓派）只下发一段段"车体坐标系的相对位移"指令，下层（A 板 STM32）用轮式里程计闭环执行；
树莓派端用 `WorldModel` 把每段相对位移累加成全局期望位姿做漂移监测，到位判定、断点续跑、漂移修正
全部由世界模型与行为节点自动完成。全程**没有 SLAM、没有雷达、没有全局定位**，黑线和 6 个
AprilTag 目前软件完全未使用。

### 1.2 一次"轨迹段"的完整数据流

```
mission_config.py  GLOBAL_CONFIG.trajectory   ← 路径就定义在这里（19 段列表）
        │
        ▼
environment/world_model.py  WorldModel
   · get_current_segment()      取当前段
   · current_segment_remaining() 把"本段终点 - 里程计当前位置"换算回车体坐标 (dx,dy,dyaw)
   · is_current_segment_reached() 按主运动轴判定到位（防麦轮横移串扰误判）
   · advance_segment()          段完成后把位移旋转到世界系累加进 expected_pose
        │
        ▼
behavior_tree/custom_actions.py  DriveSegmentAction（状态机）
   IDLE → (必要时 STOPPING→CONFIGURING) → MOVING → COMPLETE 判定 → 交还世界模型推进
   · 板端拒绝 busy_or_range/stop_required/cancelled → 按剩余位移重发（不 stop）
   · saw_running 保护：move 刚发出时读到的是上一段残留终态，必须等板端真正进入 RUNNING(1)
        │
        ▼
core/protocol.py + core/chassis_driver.py
   format_move_cmd(dx,dy,dyaw) → A 板 ASCII 协议 115200，板端里程计闭环执行
   下行 odom 遥测 ~100ms 一帧：rel_x, rel_y, rel_yaw, vx, vy, wz, safety_state, motion_state
```

### 1.3 行为树组装（`missions/main_mission.py`）

行为树长度**自动跟随轨迹段数**：`for i in range(len(world_model.trajectory))` 逐段生成
`DriveSegmentAction`，再按 `GLOBAL_CONFIG.pick_tasks` 的配置在指定段之后插入 `VisualPickAction`。
开头是 `ResetOdomAction`（里程计清零，与世界模型对齐），结尾是 `StopAction`。

当前默认 `pick_tasks`：段 3（left_0.5m，到达屋顶材料区）后抓 1 块紫色（YOLO 类
`Purple_Block`，机械臂动作组 1）。视觉链路未连通或机械臂未连接时**自动退化纯轨迹模式**。

### 1.4 当前 19 段去程轨迹及含义

方向约定：`dx` 前进为正、`dy` 左移为正（麦轮横移）、`dyaw` 逆时针为正；
每段只做一个维度的运动（纯平移或纯旋转），防止耦合漂移。

### 1.5 配套安全与限幅（与"加路径"直接相关）

| 参数 | 位置 | 当前值 | 说明 |
|------|------|--------|------|
| `max_x_m / max_y_m` | `ChassisLimitConfig` | 3.0 / 3.0 | 单次 move 位移上限；**A 板默认只有 2m**，靠握手时下发 motion_cfg 抬升，新增单段位移 >3m 会被拒 |
| `max_velocity_m_s` | 同上 | 0.40 | 全局统一速度，**当前不支持按段设速** |
| `position_tolerance_m` | 同上 | 0.005 | 板端完成容差（5mm） |
| `arrival_tolerance_m` | 同上 | 0.03 | 行为树到位判定（3cm，容忍横移串扰） |
| `max_duration_ms` | 同上 | 30000 | 单段超时 30s |
| `mission_timeout_s` | `MissionConfig` | 300 | 任务级看门狗：整树超时强制停车（比赛 6 分钟） |
| auto_keepalive | `chassis_driver` | ~50ms | 自动动作期间必须周期保活，否则板端判链路超时（motion=4） |

## 二、⭐ 后续要添加路径怎么改（双机版操作步骤）

> 旧单机版的做法（改 `DEFAULT_TRAJECTORY`/`RETURN_TRAJECTORY` + 在 `main_mission.py`
> 里写死 `if i == 3` / `if i == 18`）**已过时**。双机版把"动作插在哪一段之后"也搬进了配置。

### 2.1 最常见的场景：只加位移段（纯轨迹）

**只改 1 个文件：`rb_zcode/树莓派/robogame_project/config/mission_config.py`**

在 `MissionConfig.trajectory` 的默认列表里插入/追加 `TrajectorySegment` 即可：

```python
TrajectorySegment(name="build_shift_right", dx=0.0, dy=-0.25, dyaw=0.0),
```

行为树会自动多出一个 DriveSegment，`WorldModel` 自动处理坐标变换与到位判定——
**`world_model.py`、`bt_engine.py`、`main_mission.py` 都不用动**。

坐标系速记：
- `dx>0` 前进 / `dx<0` 后退；`dy>0` 左移 / `dy<0` 右移；`dyaw>0` 逆时针 / `<0` 顺时针
- 90° = 1.5708 rad，180° = 3.1416 rad
- 继续遵守"一段一个维度"的既有约定，不要写复合位移段
- 单段位移不要 ≥3.0m（`max_x_m/max_y_m` 限幅；过长就拆两段）

### 2.2 场景二：走到某处后要"视觉抓一块"

**还是只改 `mission_config.py`**，往 `MissionConfig.pick_tasks` 里加一行 `PickTask`：

```python
from core.arm_driver import ArmDriver   # 引用动作组常量更可读

pick_tasks: List[PickTask] = field(default_factory=lambda: [
    PickTask(after_segment=3, target_class="Purple_Block", arm_group=ArmDriver.GROUP_CATCH_PURPLE_TO_LEFT),
    # ★ 新增：段 9（forward_2m 穿越走廊后）抓远侧橙色块
    PickTask(after_segment=9, target_class="Orange_Block", arm_group=ArmDriver.GROUP_CATCH_FAR_ORANGE_LEFT),
])
```

`PickTask` 三个字段：
- `after_segment`：第几段（**0 起数**）跑完后插入抓取；
- `target_class`：YOLO 类别（`best.pt` 当前只有 `Purple_Block` / `Orange_Block` 两类）；
- `arm_group`：机械臂动作组编号（**必须已烧录进 STM32**，0x06 无应答帧，执行完按 `grip_wait_s=12s` 盲等）。

机械臂动作组常量表（`core/arm_driver.py`）：

| 组号 | 常量 | 含义 |
|------|------|------|
| 1 | GROUP_CATCH_PURPLE_TO_LEFT | 抓紫色块到左侧框 |
| 2 | GROUP_LEFT_TO_PLATFORM | 左侧紫块放平台 |
| 3 | GROUP_PLATFORM_TO_MIDDLE | 平台紫块抓到中间框 |
| 4~6 | GROUP_CATCH_FAR_ORANGE_LEFT/MIDDLE/RIGHT | 抓远侧橙色块 |
| 7~9 | GROUP_CATCH_NEAR_ORANGE_LEFT/MIDDLE/RIGHT | 抓近侧橙色块 |
| 10~15 | GROUP_BUILD_1~6 | 搭建第 1~6 层 |
| 16/17 | GROUP_LEFT_TO_MIDDLE / GROUP_RIGHT_TO_MIDDLE | 框间转移 |

注意：同一类块连续抓两次时，抓取姿态会随载具状态变化——多块抓取编排（如紫→橙→橙）
需要结合 2/3/16/17 号转移组一起设计，先在真机验证动作组串联再上比赛逻辑。

### 2.3 场景三：到达搭建区后要"机械臂搭建"

双机版目前**没有**搭建动作节点（单机版的 `ArmBuildAction` 没有搬过来）。两种接法：

**方法 A（推荐，配置化）**：仿照 `PickTask` 的思路扩展——在 `mission_config.py` 加一个
`ArmTask(after_segment, arm_group, duration)` 数据类，在 `main_mission.py` 的循环里
按 `after_segment` 索引插入（与 `pick_map` 同款写法）。好处：以后加第二层、第三层
（GROUP_BUILD_2/3…）全都是加配置行，不再改行为树代码。

**方法 B（最快）**：把单机版 `robogame_project/behavior_tree/custom_actions.py` 里的
`ArmBuildAction` 类复制进双机版同名文件，然后在 `main_mission.py` 循环里按段号插入：

```python
from behavior_tree.custom_actions import ArmBuildAction
...
    if i == 18 and arm:   # 段 18 = forward_2.6m 到达搭建区
        actions.append(ArmBuildAction(chassis, arm,
                       group_id=ArmDriver.GROUP_BUILD_1, duration=12.0))
```

### 2.4 场景四：全新行为能力（如标签矫正、巡线辅助）

继承 `BTNode` 写新叶子节点（放 `custom_actions.py`），再按 2.3 的方式挂到某段之后。
参考模板：`VisualPickAction`（状态机 + 失败安全停车）、`ArmBuildAction`（先锁底盘再动作）。

### 2.5 ⚠️ 三个最容易踩的坑

1. **段序号移位**：`pick_tasks.after_segment` 和手写 `if i == N` 都依赖"段在列表里的
   下标"。**在列表中间插段会让后续所有下标 +1**，已配置的抓取点会悄悄错位。对策：
   - 新路径段尽量**追加到列表尾部**或在设计时就定好下标；
   - 改完配置先跑仿真核对终点与抓取点（见 2.6）；
   - 更彻底的办法是把 `PickTask.after_segment` 改成按 `name` 匹配（`main_mission.py`
     里 `pick_map = {seg.name: task}`），改动量约 5 行。
2. **单段限幅**：A 板出厂默认单次位移 ≤2m，靠 motion_cfg 抬到配置的 3.0m；新段超过
   3.0m 会稳定收到 `move:busy_or_range`（驱动会重发剩余位移，但会拖慢节奏）。
3. **返回/多趟闭环**：双机版已删除旧版的 `RETURN_TRAJECTORY` 和
   `get_mission_trajectory()`。要做"搭建区→物料区→搭建区"多趟，把返程段直接追加进
   `trajectory` 列表（旋转段会自然处理朝向），并在 `pick_tasks` 里配置第二趟的抓取点；
   载量（≤3 块、紫 ≤1）的约束目前**没有**接进决策，需自己保证每趟配置合法。

### 2.6 改完之后的验证闭环（必做）

```bash
cd rb_zcode/树莓派/robogame_project
python3 _sim_test_headless.py     # 无头仿真：纯轨迹全流程 + 暂停/恢复，核对终点位姿
```

- 仿真用 `SerialConfig.simulate=True` 的 Mock 底盘，`sim_time_scale=10` 加速；
- 核对三件事：①最终 rel_x/rel_y/rel_yaw 与设计一致；②漂移误差 0；③抓取点插入日志
  （`[Mission] 段 N 后插入视觉抓取：...`）顺序正确；
- 真机前再过一遍《改动报告.md》3.3 节的 4 项标定清单（u_sign/v_sign、0x06 帧格式、
  ARMED 时序、target_u/v 复核）。

## 三、实车偏差问题：为什么车"意识不到"，不加硬件能做什么（2026-09-26 增补）

> 实车反馈：19 段可跑通，但运动过程出现大偏差，车自身无感知。本节给出根因分析与
> **零硬件**层面的对策；加独立传感器的根治方案见《比赛导航方案调研与设计.md》第四节。

### 3.1 根因：控制与"感知"同源，物理偏差对系统不可见

现在的闭环是**自证闭环**：

```
move 指令 → A 板按【自己的轮式里程计】判定到位 → 上层 drift_error() 拿【同一套轮式里程计】
与期望位姿比对 → is_current_segment_reached() 判的是"里程计到位"而非"物理到位"
```

整条链路里**没有任何独立于驱动轮的测量**。轮子打滑、麦轮横移侧滑时，里程计报的位移
≠ 物理位移，板端照样报 COMPLETE，上层照样判到位——车"意识不到"不是代码 bug，是
**感知维度缺失**。这不是调参数能根治的，但下面三件事能先消掉大头。

### 3.2 对策一：三系数标定（零硬件、收益最大、先做）

麦轮横移侧滑是**系统性、可标定**的误差——FTC/Road Runner 社区的标准调参流程就是给
里程计分三个系数实测修正，横移的 lateral multiplier 典型值在 **1.1~1.3**（即横移时
轮式里程计普遍少报 10%~30% 物理位移）。对到场地的卷尺实测流程：

| 测试 | 方法 | 得到的系数 | 预期问题最大的 |
|------|------|-----------|---------------|
| 前移标定 | 前进 2m（卷尺/场地标线），记录 rel_x | 前移比例 = 实际 / 报告 | 较小 |
| 横移标定 | 横移 2m，记录 rel_y | **横移比例** = 实际 / 报告 | ★ 最大（侧滑） |
| 旋转标定 | 原地转 90°×4，读 rel_yaw 累计 | 旋转比例、yaw 残差 | 中 |
| 往返漂移测试 | 横移 2m 再回来，往复 3 次读 rel_y 残差 | 漂移指标（应为 ~0） | — |
| 速度相关性 | 同距离全速 vs 半速横移对比系数 | 确认侧滑随速度增大 | 决定限速值 |

**修正落点二选一**：
- 治本：把系数改进 **A 板固件的里程计解算**（找底盘固件同学，改完所有上层逻辑零改动）；
- 治标：上层在 `mission_config.py` 给 `TrajectorySegment` 加每轴缩放（或在写入轨迹时
  预乘），把横移段 dy 按实测比例放大/缩小。注意：**move 停止判据在板端**，上层只能
  改"发多少"，所以比例必须让板端报告值与物理值对齐——标定后务必用往返测试复核。

### 3.3 对策二：降速与拆段（压制侧滑）

侧滑随速度与加速度增大。当前 `max_velocity_m_s=0.40` 全局统一、2.75m 长横移一杆到底，
是最容易甩出偏差的组合：
- 把长横移段拆成 2 段（中途世界模型自动校核），并实测找出"能接受的时间 vs 偏差"的
  最优速度（预计 0.25~0.30 m/s 显著更稳）；
- 若后续按第四节给 motion_cfg 加了按段限速，走廊可保 0.4+，工位接近 0.15。

### 3.4 对策三：让车至少"报警"（可感知化改造）

在独立传感器到位之前，先用现有遥测把"看不见"变成"能告警"，比赛时人工决策
（规则允许异常处理：搬回启动区静置 6s 重跑）：

- **打滑征兆计数**：DriveSegmentAction 里"报 COMPLETE 但未到位，按剩余位移修正"的
  重发次数已在发生——把每段的重发次数累计上报，单段 ≥2 次即告警（这就是打滑最直接
  的内部信号）；
- **段耗时监控**：每段实测耗时 vs 按限速的理论耗时，超 1.5 倍告警；
- **drift_error() 阈值告警**：每段完成后超阈值（如 0.05m）在 GUI 高亮提示；
- 以上做成一个轻量统计类挂进现有日志/GUI，**不改行为树结构**。

### 3.5 根治必须加独立测量源

零硬件对策只能消除系统性误差与"盲跑"，无法感知纯物理滑动。根治路线（独立观测 →
纠偏 → 全局重定位）与硬件选型见《比赛导航方案调研与设计.md》第四节——但比赛临近，
**锚点/IMU/雷达等新感知系统默认冻结为赛后项**，赛前取舍以其 4.5 冲刺版方案为准。

### 3.6 时间不足时的执行原则（比赛冲刺版，2026-09-26）

比赛临近，执行顺序以《比赛导航方案调研与设计.md》4.5 冲刺版方案为准，要点：

1. **冻结新感知系统**（标签、IMU、雷达全部赛后）——赛前只做三件事：少跑路（路线瘦身）、
   消系统差（三系数标定）、放大容差（工位设计成伺服可达）；
2. **改动只落在低风险位置**：`mission_config.py`（限速、删冗余微调段、加橙块支线）、

4. 每次摆车**贴启动区同一角**——初始位姿一致性是免费的精度；
